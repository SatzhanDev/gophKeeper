# GophKeeper

Клиент-серверный менеджер паролей: надёжное хранение логинов/паролей, произвольных
текстовых и бинарных данных, данных банковских карт с поддержкой синхронизации
между несколькими клиентами одного пользователя.

Проект реализован по ТЗ курса Yandex Practicum "Go-разработчик" (диплом).

## Архитектура

- **Транспорт** — gRPC (protobuf-контракты в `api/proto/`).
- **Хранилище** — PostgreSQL.
- **Аутентификация** — JWT, пароли хранятся как bcrypt-хэши.
- **Шифрование данных — end-to-end (zero-knowledge).** Сервер никогда не видит
  содержимое секретов в открытом виде: клиент шифрует данные ключом (DEK),
  выведенным из мастер-пароля пользователя через Argon2id, и сервер хранит
  только зашифрованные байты. Подробности схемы (DEK/KEK, envelope encryption)
  — в `internal/client/crypto`.
- **Клиент** — интерактивный CLI (один непрерывный процесс на сессию работы,
  не набор одноразовых подкоманд): после `login`/`register` ключ шифрования
  остаётся в памяти процесса до выхода, повторно вводить мастер-пароль на
  каждую команду не нужно.
- **Синхронизация** между несколькими клиентами одного владельца — клиент не
  кэширует данные локально, каждая команда обращается к серверу за актуальным
  состоянием; конфликты параллельного изменения одного секрета разрешаются
  через optimistic concurrency (поле `version`).

## Структура репозитория

```
cmd/server              — точка входа сервера (main.go)
cmd/client               — точка входа CLI-клиента (main.go)
internal/server/
  config                 — конфигурация сервера (флаги/env)
  auth                   — bcrypt, JWT
  service                — бизнес-логика (AuthService, SecretService)
  grpcserver              — gRPC-хендлеры и auth-интерцептор
  storage                 — интерфейсы репозиториев
  storage/postgres         — реализация репозиториев поверх PostgreSQL
internal/client/
  config                  — конфигурация клиента (флаги/env)
  crypto                  — вывод ключа из пароля, шифрование данных (E2E)
  grpcclient               — подключение к gRPC-серверу
  cli                      — интерактивный режим клиента
internal/pkg/
  model                   — доменные модели (User, Secret)
  version                  — версия и дата сборки клиента (ldflags)
api/proto/                — .proto контракты и сгенерированный код
migrations/                — SQL-миграции схемы БД
```

## Быстрый старт

### Требования

- Go 1.25+
- Docker (для PostgreSQL и интеграционных тестов)
- [golang-migrate](https://github.com/golang-migrate/migrate) CLI (для миграций БД)
- `protoc` + `protoc-gen-go` + `protoc-gen-go-grpc` (только если меняешь `.proto`)

### Поднять базу данных

```
docker run --name gophkeeper-pg -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=gophkeeper -p 5433:5432 -d postgres:16
```

Миграции накатываются сервером автоматически при каждом запуске (см. `cmd/server/migrate.go`)
— вручную гонять `make migrate-up` не обязательно, но команда остаётся доступна как
самостоятельный инструмент (например, чтобы применить миграции без запуска сервера).

### Сгенерировать TLS-сертификат (обязательно перед первым запуском)

gRPC-сервер всегда поднимается с TLS, самоподписанный сертификат для локальной
разработки генерируется одной командой:

```
make certs
```

Создаёт `certs/server.crt`/`certs/server.key` (не коммитятся в git, каждый разработчик
генерирует свою пару). Клиент по умолчанию ожидает этот же файл `certs/server.crt`, чтобы
доверять серверу — если запускаешь клиент из другой директории, укажи путь явно
(флаг `-tls-ca-cert` или переменная `TLS_CA_CERT_FILE`).

### Запустить сервер и клиент

```
make run-server    # в одном терминале
make run-client    # в другом
```

Адреса/секреты по умолчанию заданы в `Makefile` (`DATABASE_DSN`, `JWT_SECRET`, `GRPC_PORT`,
`SERVER_ADDR`) — переопределяются через переменные окружения или аргументы `make`:
```
make run-server DATABASE_DSN="postgres://..."
```

## Команды клиента

После запуска `gophkeeper-client` открывается интерактивная сессия:

| Команда              | Описание                                             | Нужен мастер-пароль |
|----------------------|-------------------------------------------------------|----------------------|
| `register <login>`   | зарегистрировать нового пользователя                 | да |
| `login <login>`      | войти                                                  | да |
| `list`                | показать список секретов (id, тип, метаданные)        | нет |
| `get <id>`            | показать расшифрованный секрет                        | нет (ключ уже в памяти сессии) |
| `add <type> <metadata> <данные>` | добавить секрет (`type`: `login`\|`text`\|`binary`\|`card`) | нет |
| `update <id> <metadata> <данные>` | обновить секрет                       | нет |
| `delete <id>`         | удалить секрет                                        | нет |
| `help`                 | список команд                                          | — |
| `exit` / `quit`        | выйти                                                  | — |

Мастер-пароль запрашивается один раз при `register`/`login` — дальше ключ шифрования
живёт в памяти процесса до выхода из сессии.

## Сборка

```
make build              # сервер + клиент под текущую платформу, в bin/
make build-client-all   # клиент под Linux/Windows/macOS (amd64+arm64) разом
```

Версия и дата сборки клиента зашиваются в бинарник через `-ldflags` (см. `Makefile`,
переменные `VERSION`/`BUILD_DATE`) и доступны через:
```
./bin/gophkeeper-client -version
```

## Тесты

```
make test              # юнит-тесты + покрытие (coverage.out), без Docker
make cover              # показать процент покрытия по проекту
make test-integration   # интеграционные тесты storage/postgres (нужен Docker)
```

Покрытие считается без сгенерированного protobuf-кода (`api/proto/...`) и точек
входа `cmd/...` — они не содержат бизнес-логики, которую имеет смысл юнит-тестировать.
